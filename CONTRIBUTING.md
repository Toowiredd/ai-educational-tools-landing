## Development Workflow

### ⚠️ Important: Choose Your Workflow

This project was generated by [GPT Engineer](https://gptengineer.app) and supports **two development models**. **You must choose one** to avoid merge conflicts.

#### Option A: GPT Engineer Sync (Primary for AI-Assisted Development)
- Make changes via the [GPT Engineer web interface](https://gptengineer.app)
- Changes are automatically synced to this GitHub repository
- Pull latest changes: `git pull origin main`
- **Best for:** AI-assisted rapid prototyping and feature development

#### Option B: Traditional Git Workflow
- Clone this repository locally
- Make changes in your preferred editor/IDE
- Commit and push changes to GitHub
- **Best for:** Manual development with full control

**⚠️ Do NOT mix both workflows** without coordinating with the repository owner, as this can cause merge conflicts.

**Recommendation for Contributors:** Use Option B (traditional git) and communicate with maintainers before contributing.

## Getting Started

### Prerequisites

**Required:**
- **Node.js:** 18.x or higher (install via [nvm](https://github.com/nvm-sh/nvm))
- **npm:** 9.x or higher (comes with Node.js)
- **Git:** Latest stable version

**Optional:**
- **Docker:** For containerized development
- **Docker Compose:** For simplified container orchestration

### Local Development Setup

#### Method 1: Direct Node.js Setup (Recommended)

```bash
# 1. Fork and clone the repository
git clone https://github.com/YOUR_USERNAME/ai-educational-tools-landing.git
cd ai-educational-tools-landing

# 2. Install dependencies
npm install

# 3. Start development server
npm run dev

# 4. Open your browser
# Navigate to http://localhost:8080
```

#### Method 2: Docker Setup

```bash
# 1. Clone the repository
git clone https://github.com/YOUR_USERNAME/ai-educational-tools-landing.git
cd ai-educational-tools-landing

# 2. Start Docker containers
docker-compose up

# 3. Access the application
# Navigate to http://localhost:8080
```

### Verify Installation

After starting the dev server, you should see:
```
VITE v5.0.2  ready in 423 ms

➜  Local:   http://localhost:8080/
➜  Network: http://0.0.0.0:8080/
```

## Code Style

### Formatting Rules

This project uses **Prettier** and **ESLint** for code consistency.

**Important:** Prettier is configured with an **unusual line width**:
```json
{
  "prettier": {
    "printWidth": 99999999
  }
}
```

This means **Prettier will not wrap lines**. This was an intentional choice in the original GPT Engineer generation (reason unknown). When contributing:
- Do NOT manually wrap long lines
- Let Prettier handle formatting
- Maintain consistency with existing code style

### ESLint Rules

Run linter before committing:
```bash
npm run lint
```

**Configuration:** `.eslintrc.cjs`
- **Plugins:** React, React Hooks, React Refresh
- **Rules:** Standard React best practices
- **Max Warnings:** 0 (warnings treated as errors)

### Component Conventions

#### File Naming
- Use **PascalCase** for component files: `FeatureCard.jsx`
- Use **camelCase** for utility files: `formatDate.js`

#### Component Structure
```jsx
import React from "react";
import { Box, Heading, Text } from "@chakra-ui/react";

const ComponentName = ({ prop1, prop2 }) => {
  return (
    <Box>
      <Heading>{prop1}</Heading>
      <Text>{prop2}</Text>
    </Box>
  );
};

export default ComponentName;
```

#### Props Destructuring
- Destructure props in function signature
- Use descriptive prop names
- Consider adding PropTypes or TypeScript in future

#### Chakra UI Usage
- Prefer Chakra components over plain HTML
- Use Chakra's responsive syntax: `{{ base: "column", md: "row" }}`
- Leverage Chakra's color mode: `useColorModeValue("light", "dark")`

## Making Changes

### Before You Start

1. **Check existing issues** - Avoid duplicate work
2. **Create an issue** - Discuss your proposed changes
3. **Get approval** - Wait for maintainer feedback
4. **Create a branch** - Use descriptive branch names

### Branch Naming Convention

```
feature/short-description    # New features
fix/issue-description        # Bug fixes
docs/what-you-updated        # Documentation changes
refactor/what-you-refactored # Code restructuring
test/what-you-tested         # Test additions
```

**Examples:**
```
feature/add-contact-form
fix/mobile-menu-overflow
docs/update-readme-setup
refactor/extract-feature-card
test/add-index-page-tests
```

### Development Workflow

```bash
# 1. Create and checkout a new branch
git checkout -b feature/your-feature-name

# 2. Make your changes
# Edit files in your editor

# 3. Test your changes
npm run dev
# Verify in browser at http://localhost:8080

# 4. Run linter
npm run lint

# 5. Stage and commit changes
git add .
git commit -m "Add feature: brief description"

# 6. Push to your fork
git push origin feature/your-feature-name

# 7. Create a Pull Request
# Go to GitHub and open a PR from your fork
```

### Commit Message Guidelines

Write clear, descriptive commit messages:

**Format:**
```
<type>: <short summary (50 chars max)>

<optional detailed description>

<optional footer>
```

**Types:**
- `feat:` - New feature
- `fix:` - Bug fix
- `docs:` - Documentation changes
- `style:` - Formatting (no code change)
- `refactor:` - Code restructuring
- `test:` - Adding tests
- `chore:` - Maintenance tasks

**Examples:**
```
feat: add contact form to landing page

Implemented contact form with name, email, and message fields.
Uses Chakra UI form components with validation.

Closes #42
```

```
fix: mobile navigation menu overflow on small screens

Adjusted max-width and padding for mobile viewports.
Tested on iPhone SE and Samsung Galaxy.
```

## Submitting Contributions

### Pull Request Process

1. **Ensure your code:**
   - ✅ Follows the code style guide
   - ✅ Passes `npm run lint` with no errors
   - ✅ Works in development mode (`npm run dev`)
   - ✅ Builds successfully (`npm run build`)
   - ✅ Is tested manually in browser

2. **Update documentation:**
   - Update README.md if adding features
   - Add comments for complex logic
   - Update PROJECT_HISTORY.md for significant changes

3. **Create your PR:**
   - Use a clear, descriptive title
   - Reference related issues: "Fixes #42" or "Closes #42"
   - Describe what changed and why
   - Add screenshots for UI changes
   - Tag reviewers (if known)

4. **Respond to feedback:**
   - Address reviewer comments promptly
   - Make requested changes in new commits
   - Re-request review after updates

### Pull Request Template

```markdown
## Description
Brief description of changes

## Type of Change
- [ ] Bug fix
- [ ] New feature
- [ ] Documentation update
- [ ] Refactor
- [ ] Test addition

## Checklist
- [ ] Code follows project style guidelines
- [ ] Linter passes (`npm run lint`)
- [ ] Tested manually in browser
- [ ] Documentation updated (if needed)
- [ ] No console errors or warnings

## Screenshots (if applicable)
[Add before/after screenshots for UI changes]

## Related Issues
Fixes #[issue number]
```

## Testing Guidelines

- [ ] All interactive elements work (buttons, links, etc.)

## Questions and Support

### Getting Help

**For questions about contributing:**
1. Check this document first
2. Review existing issues and PRs
3. Open a new issue with "Question:" prefix

**For bug reports:**
1. Search existing issues to avoid duplicates
2. Use the bug report template (if available)
3. Include:

   - Expected vs. actual behavior

   - Browser and OS version

**For feature requests:**
1. Open an issue with "Feature Request:" prefix
2. Describe the problem you're solving
3. Propose a solution
4. Discuss with maintainers before implementing
